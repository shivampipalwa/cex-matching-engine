# Architecture

**Project goal:** a full-fledged, low-latency centralized exchange backend in
Rust — a decoupled matching engine, an accounts ledger, Redis-backed messaging,
and (eventually) a database, REST API, and websocket feeds.

## The core idea

> The matching engine is a deterministic state machine fed by a single ordered
> log of commands, and it emits a single ordered log of events. It talks to
> nothing else directly — no database, no network, no clock it doesn't control.

Crash recovery, auditability, replayability, and independently scalable reads
all fall out of this one property. The engine's state must be a **pure
function of its input log** — replaying the same log from the start always
reproduces the same state, byte for byte.

---

## Process topology & transport

Two processes — an API gateway and a matching engine — connected through Redis:

- **Command log (API → engine): a durable Redis Stream.** This is the
  write-ahead log the engine replays to rebuild state after a crash. It must
  be persistent and replayable.
- **Result delivery (engine → API): ephemeral Redis pub/sub**, keyed by a
  correlation id. If the engine crashes before answering, the HTTP request
  simply fails and the caller retries — a stale result should never be
  replayed to a client that has already disconnected, so this leg is
  deliberately best-effort.

### Why Streams and not pub/sub for the log

| Primitive | Persists? | Replayable? | Used for |
|---|---|---|---|
| Pub/Sub | No | No | Ephemeral "notify whoever's listening now" → **result leg** |
| List (`LPUSH`/`BRPOP`) | Yes (until popped) | Not really | A simple work queue |
| Streams (`XADD`/`XREAD`) | Yes | **Yes** — append-only, read from any point | **the command log** |

Pub/sub is fire-and-forget: if no subscriber is connected, the message is
gone. It cannot serve as a durable log — but it's exactly right for the
ephemeral result return trip.

**Trade-off accepted:** a "place order" HTTP call blocks until the engine
round-trips a result back through Redis — slower and more complex than an
in-process call, in exchange for durability and process decoupling.

## Identity & the command wire format

Three distinct kinds of id, each solving a different problem:

1. **Sequence number** — an entry's position in the command log; establishes
   total order and makes replay deterministic. This comes free from Redis
   Streams: every `XADD` returns a monotonic entry id, and because Redis is
   single-threaded, the order of `XADD`s *is* the total order.
2. **Order id** — identifies an order across its life (place → fills →
   cancel). Assigned by the engine from a monotonic counter at processing
   time. A counter is safe for replay because it's a deterministic function of
   log position — unlike a random id, which would make a replayed cancel
   reference an id that no longer exists.
3. **Correlation id** — ties one request to its one response. Generated by the
   API, echoed back by the engine, then discarded.

**Round trip:**
1. API generates a correlation id, `XADD`s the command (carrying it) to the Stream.
2. API subscribes to `result:{correlation_id}` and waits.
3. Engine reads the command, assigns an order id (`counter++`) if applicable,
   matches it, and publishes the result to that channel.
4. API receives it and returns the HTTP response.

**Wire format:** each command serializes to a single JSON blob stored in one
Stream-entry field. JSON keeps the log directly inspectable
(`redis-cli XRANGE`) — useful during development, and swappable for a binary
format later without changing the design.

A separate, durable **output event stream** (trades, book deltas) lets other
services — a database writer, a websocket broadcaster — consume engine output
without the engine ever talking to them directly.

## The engine run loop

- **A single thread owns all state** — the order book, the account ledger, the
  id counter. No mutex, no shared ownership. This isn't a limitation: with a
  single thread applying commands strictly in log order, replay determinism
  and atomicity both come for free.
- **Exactly one engine instance.** Splitting the command stream across two
  engines means neither holds the whole book — an order could rest in one
  while its match arrives at the other, and they'd never meet. An exchange
  scales other ways: one engine per trading pair, read replicas for market
  data — never by splitting a single book's command stream.
- **Reads use a Redis consumer group** (`XREADGROUP` + `XACK`) even with a
  single consumer, for the Pending Entries List it provides: a command that's
  read but not yet acknowledged stays pending and can be redelivered,
  producing at-least-once delivery.

**The cycle:** read → decode → apply (mutate state) → emit (result, and later
output events) → acknowledge. One command is fully handled before the next
begins — that serialization *is* the total order.

### Emit before acknowledge

Acknowledging a Stream entry does not delete it — it only removes the entry
from the pending list. The command log itself is untouched regardless of ack
timing, so engine state is never at risk from ack timing. What ack timing
*does* control is whether a command's side effects get a second chance after a
mid-processing crash:

- Emit-before-ack risks a **duplicate** emitted event.
- Ack-before-emit risks a **lost** one — e.g. a trade the database never
  learns about, silently breaking reconciliation.

A lost event is far worse than a duplicate, so the engine emits before it
acknowledges, and downstream consumers are expected to be idempotent
(duplicate-safe): at-least-once delivery plus idempotent consumers gives
effectively-once behavior in practice.

Two guards make this concrete:
- `last_applied_seq`, tracked as engine state — the highest command sequence
  fully applied. Any command at or below that sequence is a known duplicate
  and its state mutation is skipped.
- Deterministic ids on emitted events (derived from sequence number), so a
  downstream consumer like a database writer can upsert on them and treat
  duplicates as no-ops.

### Startup and recovery

```
Phase 0 — mark the boundary
  Record the current head of the command stream. Everything at or before it
  is history; everything after is live traffic.

Phase 1 — rebuild state, silently
  Replay the log (from the start, or from the last snapshot) up to that
  boundary. Apply each command, but emit nothing — this is reconstruction,
  not new activity.

Phase 2 — go live
  Resume consumer-group reads past the boundary. Full cycle: apply, emit, ack.
```

Silent replay matters because, without it, every restart would re-emit the
engine's entire history to every downstream consumer.

A snapshot, when introduced, is a pair: `(engine_state, log_position)`.
Engine state includes the order book, the id counter, `last_applied_seq`, and
account balances — everything the engine mutates that affects future output.
Snapshots are purely a recovery-time optimization for bounding replay time;
they change where Phase 1 starts, not the shape of the recovery process.

## Balances, reserves & settlement

- **Balance checks are authoritative in the engine, not the API gateway.** The
  gateway has no serialized view of state, so two concurrent requests could
  each pass an independent check and jointly overdraw an account. The
  engine's single-threaded, in-order processing makes "check, then reserve"
  one indivisible step.
- **A trade's balance movements are atomic.** In the engine this is free — no
  half-applied trade is ever observable. In a database projection it isn't
  free, and the corresponding writes belong in one transaction.
- **Conservation:** for each currency, the sum of balance changes produced by
  a trade is exactly zero — money moves between accounts but is never created
  or destroyed. This doubles as the primary invariant for testing the ledger.
- **The engine's in-memory state is the source of truth; a database is a
  derived projection**, kept current from the engine's output event stream.
  The engine never reads the database while matching.
- Because balances must be reconstructable purely by replaying the command
  log, deposits and withdrawals are commands in that same log, sequenced
  alongside orders — the log is "everything that mutates authoritative
  state," not only order placement.

### Available vs. reserved

Each account balance, per currency, is really two numbers:

- **available** — free to spend
- **reserved** — committed to open orders, untouchable but still the
  account's own funds

Lifecycle of a buy limit order for 10 units at price 100 (requiring 1000 quote):

- **Place:** if `available ≥ 1000`, move 1000 from `available` to `reserved`.
- **Fill:** spend the reserved quote; credit the purchased base to `available`.
- **Cancel:** move whatever remains reserved back to `available`.
- **Partial fill:** consume part of the reserve; the remainder stays held
  against the unfilled quantity.

Without this split, a user could place several individually-affordable orders
that jointly exceed their balance — the reserve is what prevents that.

**Price-improvement refund:** a buy limit at 100 reserves `10 × 100 = 1000`,
but if it matches a resting ask at 95, it only pays `10 × 95 = 950`. The
difference must move from `reserved` back to `available`, or those funds are
silently locked forever with no error or crash to reveal it — only the
account slowly losing access to its own balance. Only the taker (the order
that crossed the spread) can have this discrepancy; a resting maker's reserve
always matches what it settles.

**Execution price is always the resting (maker) order's price**, never the
incoming (taker) order's limit price. Every fill produces a trade —
`{price, qty, maker, taker}` — which is both what the ledger settles against
and the granular event downstream consumers (database, websocket feeds) rely on.

## Roadmap

Built in-process first, transport swapped to Redis second: the command/result
*types* are the real boundary, and whether they travel over an in-process
channel or a Redis Stream doesn't change the engine's core logic. This kept
matching-and-money correctness and distributed-systems plumbing from being
debugged at the same time.

- **Matching engine** — price-time priority order book: limit and market
  orders, partial fills, FIFO at each price level.
- **Accounts ledger** — available/reserved balances, reserve → settle →
  refund → release, deposits and withdrawals as first-class operations.
- **Redis transport** — durable command Stream in, pub/sub results out,
  correlated by id; API gateway and engine as independent processes.
- **Crash recovery** — silent replay to a boot boundary, sequence-guarded
  against double-application.
- **Output event stream + database projection** — durable trade/event log
  consumed by a database writer.
- **REST API** — place / cancel / query balances / order book snapshot.
- **WebSocket feeds** — public market data (book deltas, trade tape) and
  private per-account order updates, both fed from the output event stream.
- **Hardening** — multiple trading pairs, latency benchmarking, observability.
